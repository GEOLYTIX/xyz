## What's Changed

### Login Server Support

- **XYZ can now act as the login server for other applications on the same domain.**
  Previously the login flow could only redirect back to a relative path inside XYZ, and the signed session cookie carried only the user object. An external service on a sibling subdomain had no way to send users to XYZ to log in, receive them back, and verify the returned token as a genuine XYZ session.

  `GET /api/user/login` now accepts a `return_to` query parameter. A successful login redirects to that location, provided it is a relative path or an absolute URL whose origin is listed in the new comma-separated `TRUSTED_RETURN_HOSTS` environment variable. When `TRUSTED_RETURN_HOSTS` is unset, no absolute URL is accepted and the redirect falls back to the application root.

  Every signed session token now includes `typ`, `iss`, and `aud` claims, configured through the new `JWT_TYPE`, `JWT_ISSUER`, and `JWT_AUDIENCE` environment variables. These default to `session`, `xyz`, and `xyz`, and `JWT_AUDIENCE` accepts a comma-separated list. The `typ` claim lets a consuming service tell a session token apart from an API key token. Existing login routes behave as before; the extra claims are the only change for current deployments.

  A new `login-public-key` npm script prints the SPKI public key derived from the RS256 `SECRET_KEY`, so the consuming application can verify tokens with it. `DEPLOYMENT.md` documents the setup in a new "Using XYZ for login" section, including the `Domain=` requirement on `COOKIE_PROPS` for subdomain deployments, and `SETUP.md` lists `TRUSTED_RETURN_HOSTS`. Thanks @AlexanderGeere! [#2954](https://github.com/GEOLYTIX/xyz/pull/2954)
