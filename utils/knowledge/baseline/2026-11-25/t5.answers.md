# XYZ API deployment questions

All paths are relative to the repository root. Environment variables are read
into the frozen global `xyzEnv` by `apps/xyz/mod/utils/processEnv.js`, which
also applies the defaults.

## 1. Signing the user token and the session cookie

The following variables control signing:

- `SECRET` is the string used to sign and verify JWTs. That covers the session
  cookie (`apps/xyz/mod/user/redirect.js`, `apps/xyz/mod/user/cookie.js`,
  `apps/xyz/mod/user/auth.js`) and the user token from `/api/user/token`
  (`apps/xyz/mod/user/token.js`).
- `SECRET_KEY` is a PEM private key. You can give the PEM inline (a value
  starting with `-----BEGIN`, with leading whitespace ignored) or as a path
  relative to the root directory (`XYZ_CWD`, or the workspace root if that is
  not set). When `SECRET_KEY` is set, its PEM replaces `SECRET`, and
  `SECRET_ALGORITHM` defaults to `RS256`. Source:
  `apps/xyz/mod/utils/processEnv.js`.
- `SECRET_ALGORITHM` is the JWT algorithm. It defaults to `HS256`, or to
  `RS256` when `SECRET_KEY` is set (`apps/xyz/mod/utils/processEnv.js`).
- The cookie itself is shaped by these variables:
  - `TITLE` is the cookie name. The default is `GEOLYTIX | XYZ`.
  - `COOKIE_TTL` sets the JWT `expiresIn` and the cookie `Max-Age`, in
    seconds. The default is `36000`.
  - `COOKIE_PROPS` holds the cookie attributes. The default is
    `Secure; HttpOnly; SameSite=Strict; Path=${DIR || '/'}`.

  Source: `apps/xyz/mod/utils/processEnv.js`, used in
  `apps/xyz/mod/user/redirect.js`.
- The JWT claims come from `JWT_TYPE`, `JWT_ISSUER` and `JWT_AUDIENCE`, which
  default to `session`, `xyz` and `xyz` (`apps/xyz/mod/utils/processEnv.js`).
  The claims are added by `apps/xyz/mod/user/jwtClaims.js`.

What happens when the variables are not set:

- **Algorithm, cookie name, lifetime and claims:** the defaults listed above
  apply. `COOKIE_TTL`, `TITLE` and `SECRET_ALGORITHM` use `||=`, so an empty
  value also falls back to the default. `COOKIE_PROPS` and the `JWT_*` claims
  use `??=`, so an empty string is kept as it is.
- **No `SECRET` and no `SECRET_KEY`:** there is no default secret.
  - `apps/xyz/mod/user/auth.js` returns `null` before verifying anything
    (`if (!xyzEnv.SECRET) return null;`). Requests that carry a token or cookie
    are therefore treated as anonymous.
  - The token is signed with `jwt.sign(..., xyzEnv.SECRET, ...)`, so issuing a
    token or session cookie fails at that call (`apps/xyz/mod/user/token.js`,
    `apps/xyz/mod/user/redirect.js`). I infer this from jsonwebtoken's
    behaviour and did not run it.

`SETUP.md` ("Troubleshooting") also says: "Check that `SECRET` or
`SECRET_KEY` is configured. Token and cookie auth depend on it."

## 2. Absolute `return_to` without `TRUSTED_RETURN_HOSTS`

The absolute URL is rejected, and the user is redirected to `${DIR}/` instead.

1. `/api/user/login` saves `return_to` in a `${TITLE}_redirect` cookie
   (`apps/xyz/mod/user/login.js`).
2. After login, `redirectLocation()` in `apps/xyz/mod/user/redirect.js`
   accepts only these targets:
   - a relative path that starts with `/` but not `//`
   - an absolute URL whose origin `trustedReturnOrigin()` finds in the
     comma-separated `TRUSTED_RETURN_HOSTS`
3. `trustedReturnOrigin()` returns `false` when `TRUSTED_RETURN_HOSTS` is not
   set. A malformed value also falls through. In both cases the location
   becomes `${xyzEnv.DIR}/`.
4. The response is still a 302 that sets the signed user cookie and clears the
   redirect cookie.

The tests in `apps/xyz/tests/mod/user/redirect.test.mjs` cover this: "falls
back to DIR for an absolute return_to whose origin is not trusted" and
"accepts an absolute return_to whose origin is in TRUSTED_RETURN_HOSTS".
`DEPLOYMENT.md` ("Using XYZ for login") puts it this way: "Unset … means no
absolute URL is ever accepted".

`TRUSTED_RETURN_HOSTS` entries are full origins, for example
`https://admin.geolytix.dev`. They are compared exactly against
`new URL(location).origin`.

## 3. Cross-origin access (CORS)

Set the `CORS_ORIGINS` environment variable. It takes a comma-separated list
of origins, for example:

```env
CORS_ORIGINS=https://cdpn.io,https://codepen.io
```

A `*` entry allows any origin. Source: `apps/xyz/mod/middleware/cors.js`, and
the `CORS_ORIGINS` JSDoc in `apps/xyz/mod/utils/processEnv.js`.

How the `cors` middleware in `apps/xyz/mod/middleware/cors.js` works:

- `apps/xyz/router.js` registers it with `router.use(cors)`, before the rate
  limiter.
- Each entry is trimmed and empty entries are dropped. If the list is empty or
  unset, the middleware does nothing.
- While `CORS_ORIGINS` is set, every response gets `Vary: Origin`.
- `Access-Control-Allow-Origin` is set to `*` when `*` is listed. Otherwise it
  is set to the request origin, but only if that origin matches an entry
  exactly.
- A preflight `OPTIONS` request from an allowed origin gets `204` with these
  headers:
  - `Access-Control-Allow-Methods: GET, POST, OPTIONS`
  - `Access-Control-Allow-Headers`, which echoes the requested headers or
    defaults to `Content-Type`
  - `Access-Control-Max-Age: 600`
- Credentials are never allowed: there is no
  `Access-Control-Allow-Credentials` header, and the cookie is
  `SameSite=Strict` by default. A cross-origin request is therefore anonymous,
  unless it provides a token explicitly as an `Authorization` header or a
  `token` param.

## 4. Database connections and how a layer selects one

**Defining connections.** Every environment variable whose name starts with
`DBS_` defines a PostgreSQL connection string. `apps/xyz/mod/utils/dbs.js`
creates a `pg` `Pool` for each one:

- The pool is keyed by the rest of the name. For example, `DBS_MAIN` becomes
  connection `MAIN`.
- Pool settings: `max: 20`, `connectionTimeoutMillis: 5000`,
  `idleTimeoutMillis: 10000`.
- Queries use `STATEMENT_TIMEOUT` and `RETRY_LIMIT`, which default to `10000`
  ms and `3` (`apps/xyz/mod/utils/processEnv.js`).

`SETUP.md` gives this example:

```env
DBS_MAIN=postgres://user:password@localhost:5432/my_database
```

The `PRIVATE` and `PUBLIC` variables are separate. They are the ACL
connection strings, not `DBS_*` entries (`apps/xyz/mod/utils/processEnv.js`).

**Selecting a connection.** A layer selects a connection with its `dbs`
property, set to the suffix of the variable name, for example
`"dbs": "MAIN"`. The value resolves in this order:

1. `layer.dbs`. If the layer does not set one, it inherits the locale's:
   `layer.dbs ??= locale.dbs` in `apps/xyz/mod/workspace/getLayer.js`.
2. When the query runs, `template.dbs` wins if the query template sets it.
   Otherwise the layer's `dbs` is used, and the workspace's `dbs` is the last
   fallback: `template.dbs ??= req.params.layer?.dbs || req.params.workspace.dbs`
   in `apps/xyz/mod/query.js`.
3. If the resolved name is not a configured `DBS_*` connection, the query
   returns `400` with "Failed to validate database connection method."
   (`apps/xyz/mod/query.js`).

So the order is: query template, then layer, then locale, then workspace.
